# Final-Round Readiness Gate

> Check an item only when evidence exists. “We intend to” is not the same as “we have demonstrated”.

## A. Compliance and eligibility

- [ ] Official guidebook and latest clarifications reviewed.
- [ ] Team/project eligibility confirmed.
- [ ] Mandatory sections and deliverables complete.
- [ ] Page/slide/time/file limits checked against exact wording.
- [ ] Links and QR codes tested using a non-team account/device where possible.
- [ ] File naming and submission portal requirements checked.
- [ ] No P0 submission blocker remains.

## B. Problem and research

- [ ] Problem maps directly to the competition brief.
- [ ] Target user is defined.
- [ ] Primary and secondary stakeholders are distinguished.
- [ ] Research method and sample are reported accurately.
- [ ] Survey percentages include numerator and denominator.
- [ ] Statistics have traceable sources and appropriate dates.
- [ ] Pain points are supported by evidence.
- [ ] Limitations and assumptions are disclosed.

## C. UX logic

- [ ] Every core feature maps to a user need.
- [ ] User journey reflects a real scenario.
- [ ] HMW is grounded and not too solution-specific.
- [ ] Information architecture is understandable.
- [ ] Primary user flow is coherent.
- [ ] Important decision points and branches are meaningful.
- [ ] Forms, feedback, error, empty, and success states are considered.
- [ ] Main flows match the prototype.

## D. Accessibility and inclusion

- [ ] Relevant user accessibility needs are identified.
- [ ] Contrast claims map to actual design colors.
- [ ] Typography and scaling are considered.
- [ ] Touch targets and motor interaction are considered.
- [ ] Icon-only actions have labels/specifications.
- [ ] Color is not the only way to communicate status.
- [ ] Assistive technology claims match actual validation.
- [ ] Privacy and dignity are addressed where sensitive data is involved.

## E. UI and prototype

- [ ] Visual hierarchy is clear.
- [ ] Design system matches actual screens.
- [ ] Component states are present where needed.
- [ ] Responsive behavior is considered.
- [ ] Prototype interactions work on the main demo path.
- [ ] No dead buttons or unexplained dead ends remain.
- [ ] Simulated behavior is not described as a live integration.

## F. Usability validation

- [ ] Test artifact and version are specified.
- [ ] Participant composition is documented.
- [ ] Tasks are realistic and neutrally worded.
- [ ] Success criteria are explicit.
- [ ] Metrics have definitions and denominators.
- [ ] SUS calculation is auditable if used.
- [ ] Accessibility testing is distinguished from general usability testing.
- [ ] Findings led to design iterations.
- [ ] Claims are proportional to the sample and method.

## G. Innovation and impact

- [ ] Competitors are relevant and current.
- [ ] Feature comparisons are sourced.
- [ ] Unknown competitor features are not marked as definitely absent.
- [ ] Differentiation matters to a target user.
- [ ] Stakeholder value proposition is clear.
- [ ] Service/operational responsibilities are mapped.
- [ ] Key dependencies and risks are identified.
- [ ] Impact outcomes and proposed measures are defined.
- [ ] Partner evidence is represented accurately.

## H. Report and pitch

- [ ] Same feature names and scope across report, deck, and prototype.
- [ ] All figures, captions, and numbering are correct.
- [ ] References support the claims they accompany.
- [ ] No placeholder or template text remains.
- [ ] Pitch fits the official time limit in a real rehearsal.
- [ ] Demo explains the user outcome, not just screen navigation.
- [ ] Backup demo asset is ready where permitted.
- [ ] Team can answer critical judge questions honestly.
